# 持续场景中的完整初始规划与当前状态恢复诊断

## 本次新增

`multiobject_pickplace_smoke.py --model-initial-plan` 将原先脚本指定的初始 pick 替换为模型完整计划中的第一个编译动作。流程为：

自然语言与图像 → 受限候选对象指代 → 完整 ModelPlan → Validator 与预测目标检查 → 编译 → 执行 pick → RGB/手部共运动持物证据 → 当前状态剩余规划 → 校验拒绝 → R1_FROM_STATE 修复 → 编译并仅执行 place。

整个成功诊断只 reset 一次。实际执行后不沿用原始 place，而是依据新持物证据重新生成剩余计划。初始规划接口只支持当前两动作 smoke 范围；不是通用多技能规划器。

v2 的四次调用分别为目标解析、完整初始规划、剩余规划、实际当前状态修复。初始计划通过 Validator 与预测目标检查。抓取 95 步，持物探测 20 步，放置 103 步；持物证据为 `holding_supported`；仅一次 pick。恢复起点为 `holding(right, blue_candidate)`，修复结果仅含 place，`executed_prefix_replayed=false`。独立模拟器评分显示蓝色方块释放后落入绿色区域。

## 必须区分的证据边界

- 初始两物体在桌面、手为空是 **controlled_scene_precondition**，不是图像估计出的状态，也不是已实现开放世界感知。
- 候选集合仍是预声明的蓝色方块与绿色区域；图像定位依赖固定颜色、相机标定和平面高度假设。
- 后续持物判断使用图像与手部本体反馈；绿色区域仍在桌面是 fixture assumption，不伪装成观测事实。
- 未知目标由程序受控注入。模型原始剩余计划是正确 place；这个例子不能用来估计自然错误率。
- 模拟器对象真值仅用于独立评分；控制器走完 waypoint 不等于已确认抓取或任务完成。
- 这里接入的是一次 `R1_FROM_STATE` 回退，不是完整 ROUTED。固定控制器也不是 ACT / AD-Flow，不构成这些策略性能证据。
- v1 与 v2 修改了输出提示，不是严格配对性能比较。已有冻结前端诊断才用于隔离修复开关，但同样只是一个受控机制对。

## 写作与下一步

可写：在限定的多物体持续场景中，完成从自然语言/图像输入、模型初始规划到观测状态剩余修复与实际放置的单例链路验证；严格输出协议失败时阻止执行。

不可写：开放世界泛化、完整视觉状态估计、自然故障总体恢复率、视觉反馈显著提高性能，或完整 ROUTED 在此场景的正式优势。

下一步先冻结这条链的协议，做少量多 seed 的无注入运行和拒绝控制；再扩展目标/位置变化与真实抓取失败的可恢复状态分支。当前未知持物仍应有限次再观测或安全停止，不能默认手空后重抓。需要正式比较时，采用相同图像与当前状态起点、相同预算的配对设置，报告每阶段拒绝、恢复调用数与独立最终评分。暂不扩展为全量 benchmark。
