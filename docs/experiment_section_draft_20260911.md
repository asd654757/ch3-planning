# 5　实验与分析（初稿）

> 本节使用两个已冻结数据集：`formal_v7_flash_prompt_protocol_20260911.jsonl` 与修正后的 `repair_pressure_formal_v8_no_oracle_20260911_153655.jsonl`。第一轮 formal_v8 因发现 oracle 泄漏，仅作诊断数据，不用于论文结果。

## 5.1　实验设置

### 5.1.1　系统流程

实验评估一个面向桌面操作任务的 VLM 计划生成与校验系统，主流程为：

```text
VLM Planner
    → 结构化 ModelPlan
    → 四层确定性校验：syntax → object → capability → state
    → 若发现不可执行前缀，则进入一次修复调用
    → 合并/替换计划
    → 目标状态检查
```

系统不依赖 VLM 自评成功。所有计划均由确定性校验器判定，任务成功定义为修复后计划通过完整校验，且目标谓词集合包含于最终离散状态。

### 5.1.2　模型与实现

- 大模型：`qwen3-vl-flash`，通过 OpenAI 兼容接口调用；
- 输入：任务文本、闭世界对象列表、目标谓词与场景图像；
- 初始规划温度：0.7；修复温度：0.3；
- formal_v7 最大生成长度为 3072 tokens，repair-pressure formal_v8 为 1024 tokens；
- 每条记录保存 prompt、prompt hash、原始模型输出、解析结果、四层校验结果、首错位置、修复前后状态、token 数与延迟，保证结果可复现审计。

### 5.1.3　实验臂与修复方式

实验 A 采用共享初始计划的对照结构：

- **B0（Direct）**：模型直接生成自由文本计划，再由解析器转换为结构化计划；
- **B1（Structured）**：模型直接输出 JSON ModelPlan；
- **B2a（+Validation）**：使用与 B1 共享的初始计划，但只加入确定性校验，发现非法即停止；
- **B2b（Ours）**：在 B2a 的基础上进一步执行一次修复调用。

修复层比较三种策略：

- **R0**：从任务描述重新生成完整计划；
- **R1**：基于损坏计划、错误信息与当前状态重新生成完整计划；
- **R2**：保留已验证前缀，只生成替换后缀，并在无已验证前缀时退化为完整计划重生成。

### 5.1.4　指标定义

- **FVR**：格式有效且通过四层校验的比例；
- **GSR**：目标状态满足比例；
- **EPR**：显式拒绝或不可行响应比例；
- **IDR**：初始计划非法检出率；
- **CRR**：非法初始计划经修复后变为合法计划的比例；
- **FRR**：合法计划被误拒或误修为非法的比例；
- **pass-but-wrong**：计划通过校验但目标状态不满足；
- **Final Task-Ready**：初始计划成功，或初始非法后修复成功的比例。

对于不可行任务，传统 FVR/GSR 天然为 0，因此另报显式拒绝比例与 pass-but-wrong。

## 5.2　formal_v7：可行性规划与不可行拒绝

### 5.2.1　数据集

formal_v7 使用 55 个任务、每个任务 5 个随机种子，共 275 个 task-seed 切片：

| 难度 | 任务数 | seed-slice 数 |
|---|---:|---:|
| easy | 10 | 50 |
| medium | 5 | 25 |
| hard | 35 | 175 |
| infeasible | 5 | 25 |
| 总计 | 55 | 275 |

实验共产生 625 条记录：B0 275 条、B1 275 条，以及 25 个非法初始计划对应的 R0/R1/R2 修复记录。

### 5.2.2　B0 与 B1 的任务表现

| 难度 | n | B0 FVR | B0 GSR | B1 FVR | B1 GSR | pass-but-wrong |
|---|---:|---:|---:|---:|---:|---:|
| easy | 50 | 100.0% | 100.0% | 100.0% | 100.0% | 0 |
| medium | 25 | 100.0% | 100.0% | 100.0% | 100.0% | 0 |
| hard | 175 | 100.0% | 100.0% | 100.0% | 100.0% | 0 |
| feasible 总计 | 250 | 100.0% | 100.0% | 100.0% | 100.0% | 0 |
| infeasible | 25 | 0.0%* | 0.0%* | 0.0%* | 0.0%* | 0 |

\*不可行任务的正确行为不是生成可执行计划，而是显式拒绝。该子集中 B0 与 B1 均为 25/25 显式拒绝，pass-but-wrong 为 0。因此表中 0.0% 是传统成功率口径，不应解释为失败。

formal_v7 中可行任务的 B0 与 B1 均达到 250/250，二者无观测差异。整体 n=275 时，两者传统 FVR/GSR 均为 90.9%，下降完全来自 25 个不可行任务。

### 5.2.3　四臂系统行为

由于 formal_v7 的所有可行任务初始计划均通过校验，修复层在可行任务上没有触发机会。因此：

- B1、B2a、B2b 在 250 个可行 task-seed 切片上的任务就绪率均为 100%；
- 修复层的 CRR 在该数据集中无法估计；
- 75 条修复记录全部来自 25 个不可行任务的防御深度检验。

在不可行任务上，R0、R1、R2 均为 25/25 显式拒绝，pass-but-wrong 均为 0。这说明系统没有在目标对象缺失时构造“看似合法但不满足原始目标”的替代计划。

### 5.2.4　model-only 拒绝与系统级拒绝消融

为区分“模型自己拒绝”和“系统校验器兜底拒绝”，对不可行任务按拒绝来源复算：

| Arm | n | 显式拒绝 | model-only refusal | deterministic guard | pass-but-wrong |
|---|---:|---:|---:|---:|---:|
| B0 | 25 | 25 | 25 | 0 | 0 |
| B1 | 25 | 25 | 10 | 15 | 0 |
| R0 | 25 | 25 | 25 | 0 | 0 |
| R1 | 25 | 25 | 25 | 0 | 0 |
| R2 | 25 | 25 | 14 | 11 | 0 |

结果表明，B0 的拒绝完全来自模型本身；B1 中 15/25 的不可行情况由确定性闭世界校验器兜底识别。R2 也有 11/25 由系统级 guard 捕获。虽然样本量较小，不能据此做强统计结论，但它说明仅依赖模型自评拒绝不可靠，闭世界校验器能够提供额外的安全层。

## 5.3　formal_v8：受控修复压力测试

### 5.3.1　动机

formal_v7 显示模型在可行任务上已经饱和。若继续在原始任务分布上比较修复方法，会出现无失败样本可修复的问题。因此引入 repair-pressure benchmark：先让 VLM 为每个可行任务生成合法 baseline plan，再由程序确定性地注入非法前缀或后缀，保证 R0/R1/R2 面对完全相同的错误分布。

压力注入方式如下：

| 压力类型 | 首个错误 | 目的 |
|---|---|---|
| `duplicate_pick_after_prefix` | `ARM_NOT_EMPTY` | 检查机械臂占用状态修复 |
| `unknown_object_after_prefix` | `UNKNOWN_OBJECT` | 检查闭世界对象约束修复 |
| `invalid_target_after_prefix` | `UNKNOWN_OBJECT` | 检查非法放置目标修复 |
| `place_before_pick` | `OBJECT_NOT_HELD` | 检查无合法前缀时的全计划修复 |
| `repeat_pick_after_valid_plan` | `STATE_TRANSITION_ERROR` | 检查仅需删除非法后缀的情况 |

formal_v8 使用 16 个可行任务：8 个 `attribute_grouped` 与 8 个 `exclusion_constraint`。每个任务取 3 个随机种子，共 48 个 task-seed 切片。48 个 baseline plan 全部合法。每个切片注入 5 类压力并分别执行 R0/R1/R2，因此修复调用总数为：

```text
48 × 5 × 3 = 720
```

### 5.3.2　总体修复结果

| Mode | n | CRR | GSR after repair | FRR | pass-but-wrong |
|---|---:|---:|---:|---:|---:|
| R0 | 240 | 41.3% | 41.3% | 0.0% | 0 |
| R1 | 240 | 100.0% | 99.2% | 0.8% | 2 |
| R2 | 240 | 55.8% | 55.8% | 0.0% | 0 |

R1 的 CRR 最高。这表示当修复器能够看到损坏计划、错误码、错误消息、当前状态和已验证前缀时，其重新生成完整计划的能力较强。R2 保留了已验证前缀，但在部分压力类型上受限于后缀生成约束，修复率低于 R1。

### 5.3.3　按压力类型分解

| 压力类型 | R0 CRR | R1 CRR | R2 CRR |
|---|---:|---:|---:|
| `duplicate_pick_after_prefix` | 41.7% | 100.0% | 58.3% |
| `unknown_object_after_prefix` | 37.5% | 100.0% | 2.1% |
| `invalid_target_after_prefix` | 41.7% | 100.0% | 89.6% |
| `place_before_pick` | 43.8% | 100.0% | 72.9% |
| `repeat_pick_after_valid_plan` | 41.7% | 100.0% | 56.3% |

R2 的主要弱点出现在 `unknown_object_after_prefix`，仅 1/48 个样本修复成功。这类压力要求替换包含未知对象的步骤；R2 的后缀输出约束使其更容易返回与锁定前缀冲突的片段，而不是重写完整计划。相比之下，R1 可以重写整个计划，因此修复成功率高。

### 5.3.4　配对显著性检验

采用 exact McNemar 检验。样本按任务 ID、随机种子和压力类型三元组严格配对，二值结果为修复后计划是否通过完整校验。

| 比较 | n00 | A only | B only | n11 | p |
|---|---:|---:|---:|---:|---:|
| R0 vs R1 | 0 | 0 | 141 | 99 | 7.17e-43 |
| R0 vs R2 | 73 | 33 | 68 | 66 | 6.41e-04 |
| R1 vs R2 | 0 | 106 | 0 | 134 | 2.47e-32 |

三组比较均显著。特别是在 R1 与 R2 的配对比较中，R1 有 106 个样本成功而 R2 失败，R2 没有出现单侧胜过 R1 的样本。

### 5.3.5　oracle 泄漏审计

受控压力测试的关键风险是修复 prompt 意外携带合法 source plan。为此对每条记录执行 prompt 级审计，提取 `original_plan` 字段并与其余记录比较：

| Mode | n | 修复结果等于 source plan | prompt 中 original = source | prompt 中 original = stress plan |
|---|---:|---:|---:|---:|
| R0 | 240 | 49（20.4%） | 0 | 0 |
| R1 | 240 | 190（79.2%） | 0 | 240 |
| R2 | 240 | 113（47.1%） | 0 | 240 |

R0 本身不接收 `original_plan`。R1 与 R2 的 240 条 prompt 中，`original_plan` 全部为损坏后的 stress plan，而非合法 source plan。R1 中较高的 exact-match 数量不构成泄漏证据；这些任务的合法修复方案具有较强的规范性，模型修复后回到同一条合法计划是合理现象。

### 5.3.6　外部基线对比

为进一步检验修复增益并非仅由“多调用一次模型”带来，本文在 formal_v8 的同一组 240 个受污染案例上增加两类外部基线。为避免初始规划随机性引入偏差，两个基线直接复用 formal_v8 冻结集合中的 stress plan，而不是重新生成 baseline。评估指标、四层校验器与目标检查器与 R0/R1/R2 完全一致。

- **Self-Refine**：给模型损坏计划、任务描述、对象列表、目标与当前状态，让其自检并返回一次完整修复计划；不提供 validator 错误码、首错位置或已验证前缀。
- **AutoTAMP-style checker-loop**：在确定性 checker 反馈下进行全计划重生成，最多 2 轮；反馈包含错误码、错误层、错误消息、首错位置与已验证前缀 step id，但没有 R2 的前缀锁和后缀输出约束。

两类基线均使用同一 VLM `qwen3-vl-flash`、同一 JSON 解析协议和同一 1024-token 上限。失败仍按 parser/schema/validation 结果判定，不做宽松重解释。

#### 总体对比

| Method | n | CRR | GSR after repair | FRR | pass-but-wrong | tokens | avg rounds |
|---|---:|---:|---:|---:|---:|---:|---:|
| R0 | 240 | 41.3% | 41.3% | 0.0% | 0 | 242,248 | 1.00 |
| R1 | 240 | 100.0% | 99.2% | 0.8% | 2 | 419,859 | 1.00 |
| R2 | 240 | 55.8% | 55.8% | 0.0% | 0 | 399,193 | 1.00 |
| Self-Refine | 240 | 57.1% | 55.8% | 1.2% | 3 | 291,264 | 1.00 |
| Checker-loop | 240 | 79.6% | 79.6% | 0.0% | 0 | 396,693 | 1.29 |

Checker-loop 是最强的外部基线，显著优于 R0 和 R2，但仍明显低于 R1。Self-Refine 与 R2 的总体成功率接近，说明只让模型自评并不能稳定利用计划错误。

#### 按压力类型对比

| 压力类型 | R0 | R1 | R2 | Self-Refine | Checker-loop |
|---|---:|---:|---:|---:|---:|
| `duplicate_pick_after_prefix` | 41.7% | 100.0% | 58.3% | 64.6% | 72.9% |
| `unknown_object_after_prefix` | 37.5% | 100.0% | 2.1% | 54.2% | 62.5% |
| `invalid_target_after_prefix` | 41.7% | 100.0% | 89.6% | 93.8% | 93.8% |
| `place_before_pick` | 43.8% | 100.0% | 72.9% | 54.2% | 91.7% |
| `repeat_pick_after_valid_plan` | 41.7% | 100.0% | 56.3% | 18.8% | 77.1% |

R2 在 `unknown_object_after_prefix` 上仅成功 1/48，而 Self-Refine 与 Checker-loop 分别成功 26/48 和 30/48。这进一步支持 5.4.3 的判断：R2 的主要限制不是模型能力不足，而是前缀锁迫使模型只输出后缀时，无法自然替换已经锁定的非法相关片段。

Self-Refine 在 `repeat_pick_after_valid_plan` 上只有 9/48 成功，显著弱于 Checker-loop 的 37/48。该类错误发生在合法动作序列末尾，只靠模型自评较难发现终态违反；确定性 checker 提供的错误反馈能有效缓解该问题。

#### 配对显著性检验

按 `(task_id, seed, pressure_type)` 与 formal_v8 严格配对，二值结果为修复后计划是否通过完整校验，使用 exact McNemar 检验：

| 比较 | A only | B only | p |
|---|---:|---:|---:|
| Self-Refine vs R0 | 63 | 25 | 6.27e-05 |
| Self-Refine vs R1 | 0 | 103 | 1.97e-31 |
| Self-Refine vs R2 | 54 | 51 | 0.845 |
| Checker-loop vs R0 | 104 | 12 | 1.87e-19 |
| Checker-loop vs R1 | 0 | 49 | 3.55e-15 |
| Checker-loop vs R2 | 78 | 21 | 6.88e-09 |

结果说明：Checker-loop 显著优于 R0/R2，Self-Refine 显著优于 R0，但 Self-Refine 与 R2 无显著差异；R1 仍显著优于两个外部基线。

## 5.4　讨论

### 5.4.1　结构化链路的价值

formal_v7 中 B0 与 B1 在可行任务上均达到 100%，因此不能声称结构化输出在传统成功率上优于自由文本。结构化链路的价值主要体现在三点：

1. 输出可直接进入确定性校验器；
2. 错误可定位到 syntax/object/capability/state 层；
3. 不可执行计划能够被系统级 guard 捕获，而不依赖模型主动承认错误。

### 5.4.2　拒绝机制的安全性

formal_v7 的不可行子集显示，系统可以稳定输出显式拒绝并消除 pass-but-wrong。但该结论只适用于当前闭世界、目标对象缺失型不可行任务，不能直接推广到开放世界感知误差、物理不可达或语义歧义等更复杂不可行情形。

### 5.4.3　前缀保护并非普遍优于全计划重生成

受控 repair-pressure 结果不支持“前缀保护一定带来更高修复率”的结论。R2 的作用在于保留已验证前缀、降低对已完成动作的改动风险，但在需要改写与未知对象相关步骤时，其后缀约束反而限制了修复空间。R1 因能重新生成完整计划，在当前五类压力上表现更强。

因此本文对 R2 的定位应是：一种面向执行安全的保守修复接口，而不是普适最优修复策略。若希望提升 R2 的修复率，可继续研究“保留前缀 + 局部重写范围自动扩大”的混合策略。

### 5.4.4　实验成本

formal_v7 全部 625 条记录共消耗 730,819 tokens，平均延迟约 5.2 s。formal_v8 的 720 次修复调用中，输入 tokens 为 890,982，输出 tokens 为 170,318，总计 1,061,300 tokens；该数字不含 48 次 baseline 生成调用的额外消耗。

在相同 240 个压力案例上，外部基线共消耗 687,957 tokens：Self-Refine 为 291,264，Checker-loop 为 396,693；Checker-loop 平均使用 1.29 轮。R0/R1/R2 分别消耗 242,248、419,859 和 399,193 tokens。因此 Checker-loop 的成本接近 R2，低于 R1，但修复率仍低于 R1。

## 5.5　当前局限

1. **单模型结果**：所有正式结果均使用 `qwen3-vl-flash`，尚不能推广到其他 VLM 或更大规模模型。
2. **仿真验证为主**：计划成功由离散状态模拟器和目标检查器判定，尚未执行真实机器人动作。
3. **任务域有限**：当前任务集中在闭世界桌面 pick/place，未覆盖开放世界物体、连续抓取失败、感知遮挡与人机干扰。
4. **不可行类别单一**：formal_v7 的不可行任务主要是目标对象缺失，不能代表全部不可行类型。
5. **R1/R2 差异可能与 prompt 设计耦合**：R2 的后缀约束是本文实现的一种具体形式，结论不宜外推到所有前缀保护机制。
6. **外部基线为协议级复现**：Self-Refine 与 Checker-loop 使用同一模型和统一 parser，但不是对应原论文系统的完整重实现；宽松输出重解释可能会改变其绝对成功率。

## 5.6　可写入论文的核心结论

1. 在闭世界桌面 pick/place 任务上，系统级确定性校验能够稳定识别非法计划并定位首错层。
2. 当可行任务达到 100% 成功率后，传统 benchmark 不再适合比较修复方法；受控压力注入能够重新制造可比较的错误分布。
3. model-only 拒绝存在漏检，闭世界 guard 可在 B1 与 R2 中额外捕获 15/25 与 11/25 的不可行情况。
4. 在五类受控修复压力下，R1 显著优于 R0 与 R2；R2 虽然保留已验证前缀，但受后缀生成限制，在未知对象替换场景中失败最严重。
5. 修复 benchmark 必须进行 prompt 级 oracle 泄漏审计；本文修正后的 formal_v8 已确认 R1/R2 只看到损坏计划，而未看到合法答案。
6. 外部基线显示确定性 checker 反馈具有重要价值：Checker-loop 达到 79.6% 并显著优于 R0/R2，但仍低于 R1；这表明完整结构化反馈与任务级重生成比单纯增加调用轮数更关键。
