# 固定单臂接口下的完整难度pilot结果

原始数据：`data/collections/recovery_difficulty_pilot_v4_20261002_140919.jsonl`。45条完整，无审计错误，纯符号评估。新脚本`analyze_recovery_difficulty.py`报告完整性、首轮/二轮结果、调用与token、候选拒绝类别；不把候选拒绝数当任务数。

两个模型设置均最多2次调用机会。重采样共20次调用、10460token；反馈共20次调用、11561token。反馈首轮10/15，二轮挽救5例；重采样首轮10/15，二轮挽救1例。按案例最终结果反馈胜4、负0、相同11。所有候选拒绝均OBJECT_NOT_HELD，无schema字段缺失拒绝。

关键发现：去掉硬件常量的模型输出负担后，最简单任务不再因arm缺失失败；多目标与部分完成开始触发真实状态前置条件错误。反馈能恢复部分候选，是值得继续检验的线索，不是正式性能或显著性结论。

重要混杂：两模型设置的首轮请求共享信息，但实际分别调用服务；即使decode seed相同，首轮结果可能不同。partial中首轮通过数为重采样2/5、反馈3/5，constrained为3/5与2/5。因此最终差异不能全部归因于第二次反馈。下一步严格的机制消融应冻结一个共同首轮候选，再将同一拒绝候选分配给无反馈第二次生成与具体错误反馈生成。候选冻结只用于机制消融，不包装为端到端在线结果。无反馈同种子重采样可能重复，不视为独立随机样本；若更改seed必须新版本并同等给予两个设置。

5个案例是对象角色排列而非5个物理布局。任务模板数量很少，不增加重复次数后声称跨任务泛化，也不合并前面v1-v3结果。

物理后端仍未完整支持本套三个独立目的区域及全部候选连续恢复。先进行固定参考计划的多物体持续执行可行性验证，不直接启动物理formal，更不能把15/15写成机器人实际成功率。

下一步顺序：共享失败候选的严格反馈消融 → 固定多物体执行可行性与独立终点评分 → 相同场景下接入模型候选，失败拒绝保留分母。已达到更难规划pilot的接口稳定条件，尚未达到多物体正式仿真的完整条件。
